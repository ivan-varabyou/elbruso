Иван, давай сформулируем бизнес‑требования так, как их формулируют в реальных проектах уровня Минспорта, FIBA DataHub или SAP Sports One.
Это не техническое ТЗ и не ERD — это то, что система обязана делать, чтобы быть полезной, масштабируемой и заменяющей Excel.

Я соберу требования в логические блоки, чтобы они были понятны руководству, аналитикам, разработчикам и федерациям.

🎯 1. Цель системы
Создать централизованную платформу оценки развития баскетбола (и потенциально других видов спорта) по регионам, дисциплинам, полу и возрастным группам, обеспечивающую:

прозрачность данных,

единые правила расчёта,

удобный ввод информации,

автоматизацию подсчётов,

аналитику и сравнение регионов,

возможность расширения без изменения архитектуры.

🧩 2. Основные бизнес‑функции системы
2.1. Управление справочниками (география, спорт, организации)
Система должна:

хранить страны, округа, регионы, типы регионов;

хранить виды спорта, дисциплины, пол, возрастные группы;

хранить организации (национальные, региональные федерации, лиги, клубы);

поддерживать иерархию организаций (например: РФБ → региональная федерация → клуб → команда);

хранить источники данных (Росстат, Минспорт, РФБ и т.д.).

Бизнес‑ценность: единая база, без дублирования, без ручного ввода.

2.2. Управление показателями (критериями)
Система должна позволять:

создавать и редактировать группы показателей (Региональная федерация, Профессиональный спорт, Массовый спорт, Судьи и т.д.);

создавать и редактировать показатели:

название,

описание,

вес (баллы за единицу),

тип значения (число/да/нет),

дисциплина (5х5/3х3),

пол,

возраст,

учёт населения (да/нет),

источник данных;

включать/выключать показатели для конкретных федераций;

изменять веса без потери исторических данных.

Бизнес‑ценность: гибкость, возможность менять правила без переписывания Excel.

2.3. Сбор данных от регионов/федераций
Система должна:

предоставлять регионам/федерациям форму ввода данных по показателям;

показывать только актуальные показатели для конкретного региона/сезона;

позволять вводить:

числа,

булевые значения,

комментарии,

при необходимости — файлы/документы;

фиксировать, кто и когда ввёл данные;

поддерживать статусы:

черновик,

отправлено,

проверено.

Бизнес‑ценность: единый процесс сбора данных, без Excel‑файлов, без потерь.

2.4. Хранение значений показателей
Система должна хранить:

регион/федерацию,

сезон,

показатель,

значение,

источник,

дату ввода.

Бизнес‑ценность: историчность, возможность сравнивать сезоны.

2.5. Автоматический расчёт баллов и рейтингов
Система должна:

автоматически рассчитывать баллы по каждому показателю:

value × weight,

если “учёт населения = да” → нормализовать на население региона;

суммировать баллы:

по группам показателей,

по дисциплинам (5х5/3х3),

по полу,

по возрасту,

общий итог;

формировать рейтинг регионов по сезону;

формировать отчёты по группам (например, “Судейство 5х5”).

Бизнес‑ценность: прозрачность, автоматизация, отсутствие ошибок Excel.

2.6. Аналитика и отчёты
Система должна предоставлять:

сравнение регионов по любому показателю;

сравнение регионов по группам показателей;

динамику по сезонам;

тепловые карты (сильные/слабые стороны региона);

экспорт данных в Excel/CSV;

API для BI‑систем (PowerBI, Tableau).

Бизнес‑ценность: аналитика для принятия решений.

2.7. Версионирование критериев
Система должна:

хранить версии показателей (вес, формулировка, правила);

обеспечивать корректный пересчёт прошлых сезонов;

позволять менять правила без потери истории.

Бизнес‑ценность: стабильность и корректность данных.

2.8. Управление доступом (RBAC)
Система должна поддерживать роли:

Администратор (РФБ)

Аналитик

Региональная федерация

Просмотр (только чтение)

Бизнес‑ценность: безопасность и контроль.

2.9. Масштабируемость
Система должна:

поддерживать добавление новых видов спорта;

поддерживать добавление новых дисциплин;

поддерживать добавление новых стран;

не требовать изменения структуры БД при добавлении новых показателей.

Бизнес‑ценность: долгосрочная жизнеспособность.

🧨 3. Ограничения и принципы
3.1. Не хранить команды, игроков, клубы (на первом этапе)
Только агрегаты:

количество команд,

количество воспитанников,

количество призовых мест.

3.2. Не хранить матчи, результаты, статистику игроков
Это другой уровень детализации.

3.3. Не хранить персональные данные
Система работает только с агрегированными значениями.

🧠 4. Нефункциональные требования
4.1. Производительность
расчёт рейтингов ≤ 5 секунд;

загрузка формы региона ≤ 2 секунд.

4.2. Масштабируемость
поддержка 1000+ показателей;

поддержка 100+ регионов;

поддержка 10+ сезонов.

4.3. Надёжность
ежедневные бэкапы;

аудит изменений.

4.4. Интерфейс
веб‑интерфейс;

мобильная адаптация;

удобные формы ввода.

🧩 5. Бизнес‑результаты, которые система должна обеспечить
Прозрачный рейтинг регионов по развитию баскетбола.

Сравнимость данных между регионами и сезонами.

Снижение ручной работы (нет Excel, нет ошибок).

Единая база знаний по развитию спорта.

Возможность аналитики и прогнозирования.

Гибкость в изменении критериев без ломки системы.

Поддержка 5х5 и 3х3 в одной платформе.

Готовность к расширению на другие виды спорта.
